## 1. 束制參數表達式支援 `=if(cant<0, abs(cant), 0)`

**檔案**：`src/core/ParameterStore.cpp`

### 根因
`ParameterStore::evaluate()` 底層是真正的 `QJSEngine`（JavaScript），`abs()` 早就支援
（映射到 `Math.abs`）。但 **`if` 是 JavaScript 保留字**，不能像 `sin`/`abs` 一樣用
`var if = function(){...}` 定義別名，直接呼叫 `if(...)` 會被 JS 引擎視為語法錯誤。

### 做法
- 求值前，用正則 `\bif\s*\(` 把 `if(` 呼叫改寫成內部函式 `_if(`，並在 prelude 注入
  `function _if(c,a,b){ return c ? a : b; }`。用詞界（`\b`）比對，不會誤傷
  `diff(`、`motif(` 這類含 `if` 子字串的識別字；巢狀寫法如
  `if(a, if(b,c,d), e)` 也能正確處理，因為只是重新命名函式呼叫，括號巢狀結構本身仍
  交給 JS 引擎解析。
- 額外支援 Excel 習慣的前綴 `=`（例如你範例裡的 `=if(...)`），求值前自動 strip 掉。
- `extractDependencies()` 加入 `if`/`_if`/`true`/`false` 到關鍵字排除表，避免把
  `if` 誤判成一個依賴的參數名稱。

### 驗證方式建議
編一個參數 `cant = -12`，束制運算式填 `=if(cant<0, abs(cant), 0)`，預期結果 `12`；
把 `cant` 改成 `5`，預期結果 `0`。

## 2. Construction Line 對束制的支援（含實際發現的 3 個 bug）

**檔案**：`src/cad/Sketch.h`、`src/cad/Sketch.cpp`、`src/ui/UIManager.cpp`

### 原本就正確、不需要動的部分
- `ConstraintSolver` 本來就不分 `Normal`/`Construction`，兩者一視同仁納入 DOF，可以
  被完整束制。
- `SketchLoopFinder` 已經正確用 `role != GeomRole::Normal` 排除建構線，不會污染封閉
  迴路 / 斷面輪廓判定。

### 發現並修正的 3 個實質 bug

1. **互動模式（滑鼠點兩下畫線）建構線完全無效**
   `LineCommand` 互動模式下，每畫完一段就發布 `startPoint`/`endPoint`
   （`QVector2D`）給對應事件；但原本 `command.create-sketch-construction-line` 與
   `command.create-sketch-centerline` 的 handler 卻是讀取 `args`（字串列表），
   `args.size() < 4` 恆為真，直接 return——也就是說滑鼠畫建構線／中心線，畫面上什麼
   都不會出現。

2. **打字輸入座標建立建構線，也會被誤建成一般線**
   `command.request-sketch-line`（非互動、打字座標的路徑）完全忽略呼叫端夾帶的
   `request["role"]`，永遠呼叫 `addLineGeom` 建立 `Normal` 角色的線。

3. **建構線／中心線沒有自動重合束制與封閉迴路偵測**
   一般線在 `command.create-sketch-line` handler 裡有完整的「連續線段自動加
   Coincident + 封閉迴路偵測」邏輯；建構線／中心線原本走的是完全獨立、無此邏輯的
   陽春分支，且 `addConstructionLine()`/`addCenterline()` 回傳 `void`，連 UUID 都拿
   不到，根本無從掛上束制。

### 修法
- `Sketch::addLineGeom()` 新增第 5 個參數 `GeomRole role = GeomRole::Normal`（有預設
  值，向下相容所有既有呼叫），讓建構線／中心線也能走「有 UUID、共用端點
  SketchPoint」的正規建線路徑。
- 重寫 `command.create-sketch-construction-line`／`command.create-sketch-centerline`
  兩個 handler：改讀 `startPoint`/`endPoint`，呼叫 `addLineGeom(..., role)`，並套用
  與一般線**完全相同**的自動 Coincident + 封閉迴路邏輯（沿用既有的
  `d->lineChainActive` 等追蹤狀態——這組狀態原本的重置邏輯本來就同時涵蓋這三種線，
  顯示原始設計就預期三者共用同一套追蹤狀態）。
- `command.request-sketch-line` 讀取並尊重 `request["role"]`。

### 驗證方式建議
1. 切到建構線工具，滑鼠連續點 3 個點畫兩段折線：應該能看到線出現，且兩段交界處自動
   有 Coincident。
2. 命令列輸入座標建立建構線：確認建出來的是虛線（建構線樣式），不是實線。

## 4. 束制參數 H 值的正負號代表左／右——結論：不需要新程式碼

這點純粹是**選對束制類型**的問題，程式邏輯已經支援，我沒有改任何程式碼：

- `FixedDistance`（兩點距離）用的是歐氏距離 `sqrt(dx²+dy²)`，**恆為非負**。如果把
  它的驅動值綁到一個會變號的參數運算式（例如 H 可能是負的），殘差方程式
  `sqrt(...) - value` 在 `value < 0` 時永遠不可能收斂到 0——**這正是你原本需要用
  `abs()` 把它轉正的原因**，也是本次項目 1 的 `if()` 語法真正的用武之地
  （例如 `=if(H<0, -H, H)` 或直接 `abs(H)`）。
- `FixedX` / `FixedY` / `FixedHorizDist` / `FixedVertDist` 這幾個束制的殘差方程式是
  `v[i1] - v[i0] - value`，**天生帶號**；而 `ConstraintCommands.cpp` 把運算式結果
  綁進 `constraint.value` 時完全沒有做 `abs()`。也就是說 **H 的正負號可以直接、
  原生地驅動 `FixedHorizDist`**，不需要任何新程式碼。

### 建議做法
1. 建立 H 這個左右偏移量時，選用 **水平距離束制（FixedHorizDist）**，而不是一般的
   兩點距離束制。
2. **固定取點順序**：務必讓 `refs[0]` 永遠是「基準點」（例如中心線上的點），
   `refs[1]` 永遠是「目標點」——這樣 `H > 0` 會自然對應右（+X），`H < 0` 對應左（−X），
   不會因為畫圖時點選順序不同而忽左忽右。目前 UI 從「量測值」轉「驅動值」時，
   顯示的量測值用了 `std::abs()`（純顯示用途），但這不影響 solver 真正吃進去的
   帶號 `value`，所以不影響這個做法。

如果你希望有第三種選擇（例如同一個 H 參數要同時驅動一個「距離永遠正」的束制 +
一個「方向」的獨立狀態，例如透過對稱束制或條件式翻轉幾何），這是可行的，但需要
另外設計，屬於比較大的改動，目前沒有實作，只是提出來供你評估要不要走這條路。

## 3. Sketch / Alignment 編輯的 Undo/Redo + 工具列按鈕

### 已有的基礎建設（本來就存在，不是本次新增）
- `UIManager::undoStack()`：全域唯一的 `QUndoStack`。
- `command::AlignmentEditCommand`：JSON 快照式 `QUndoCommand`，`before`/`after` 各
  存一次 `AlignmentDocument::toJson()`，undo/redo 時整個用 `fromJson()` 回灌，支援
  用 `mergeId` 把連續拖曳合併成一筆記錄。這套機制其實覆蓋率已經相當高：
  `addFixedTangent`/`addFixedCurve`/`addFixedSpiral`/`addFloatingCurve`/`addSCS`（3
  個 overload 中的 2 個）/`addLC`/`addCA`/`addACA`/`addCompoundChain`/
  `addReverseSpiral`/`movePI`/`moveStartPI`（拖曳，mergeId=1/2）、以及
  `AlignmentDataTableDialog` 資料表欄位編輯，全部都已經有 push。

### 本次補上的缺口

1. **`HorizontalAlignmentEdit::addSCS`（完整 7 參數 overload）沒有 push**
   （`src/railway/AlignmentDocument.cpp`）——其餘幾個 `addSCS`/`add*` 重載都有，
   唯獨這個漏掉，已補上（含正確處理其中「退化成單一圓弧就轉呼叫
   `addFloatingCurve`」的分支——那個分支本身已經會 push，不需要重複包）。

2. **縱斷面（VAlignProfileView）拖曳 VIP 完全沒有 undo**
   （`src/ui/VAlignEditorDockWidget.cpp` 的 `writeBackToTcl()`）——這是 profile view
   拖曳／新增／刪除／表單套用 VIP 後唯一的寫回入口，原本完全沒有進 undo stack。
   由於拖曳時 `vipListChanged` 會在 `mouseMoveEvent` 內逐畫面觸發，比照
   `HorizontalAlignmentEdit::movePI()` 的做法，用專屬 `mergeId=3` 把整段拖曳合併成
   一筆 Undo，不會拖一下滑鼠就在 undo stack 塞幾十筆記錄。

   > 這兩點之外，`setConstraintMode()`/`removeElement()` 這兩個
   > `HorizontalAlignmentEdit` 的方法目前在整個程式裡沒有任何呼叫端（死碼），
   > 沒有實際的 undo 缺口，本次沒有處理；之後若真的接上 UI，記得比照同一套
   > `AlignmentEditCommand::push()` 模式补上。

### Sketch 側：全新的通用快照式 undo/redo

Sketch 編輯原本完全沒有 undo/redo 骨架（除了 grip 拖曳有自己的 `GripMoveCommand`）。
沒有採取「每個 Command 手刻一個 undo/redo」的做法（那要動 LineCommand、
ConstraintCommands、刪除幾何等十幾個檔案），而是仿照 `AlignmentEditCommand` 的
JSON 快照設計，做一個**通用 hook**：

- 新增 `command::SketchEditCommand`（`src/command/SketchEditCommand.h/.cpp`），
  架構與 `AlignmentEditCommand` 完全對應：建構子吃 `before`/`after` 兩份
  `QJsonObject`，`undo()`/`redo()` 呼叫 `Sketch::fromJson()` 回灌，並額外
  透過 EventBus publish `FEATURE_UPDATED`——因為 `Sketch::fromJson()` 內部呼叫的是
  `Sketch::rebuild()` 而不是 `Document::rebuildFeature()`，後者才會 emit
  `featureShapeUpdated` 讓 `CadView::displayAllFeatures()` 觸發（這是你們自己的架構
  筆記裡提過的坑，這裡刻意繞開）。

- 在 `UIManager::initialize()`（`QUndoStack` 建立之後）掛上三個既有訊號：
  `CommandManager::commandStarted` / `commandFinished` / `commandCancelled`。
  - 指令開始時，若有作用中 Sketch，先存一次 `toJson()` 快照。
  - 指令結束（成功或取消都算）時再存一次快照，兩者不同才 `push` 一筆
    `SketchEditCommand`；相同（no-op，例如純檢視類指令）就什麼都不做。
  - 對 `LineCommand` 這種互動式多點指令（連續畫線），`commandStarted`/
    `commandFinished` 只在整個互動流程「開始」與「真正結束」（Enter/ESC/右鍵完成）
    各觸發一次，不是每點一下就觸發，所以一整段連續折線會合併成**一筆** Undo，
    行為跟大多數 CAD 軟體「一個指令一筆 Undo」一致。
  - 明確排除 `"undo"`/`"redo"` 這兩個指令名稱本身，避免呼叫復原/重做時被這個
    hook 誤判成一次新的可復原操作（那樣會讓 redo 歷史被錯誤截斷）。
  - 與 grip 拖曳、`AlignmentEditCommand` 互不衝突：兩者都是直接操作，不經過
    `CommandManager::executeCommand`，不會被這個 hook 重複捕捉。

### 工具列按鈕

在 `UIManager::initialize()` 裡新增一個獨立的「復原/重做」工具列，直接用
`QUndoStack::createUndoAction()`/`createRedoAction()` 建立 `QAction`——**刻意不走
`menu.txt` → `CommandFactory` 的通用派送路徑**，因為這兩個按鈕的 enabled 狀態、
提示文字（"復原 xxx"／"重做 xxx"）需要跟著 `QUndoStack::canUndoChanged` /
`undoTextChanged` 即時連動，用內建的 action 最單純可靠。快捷鍵設為系統標準的
`QKeySequence::Undo`/`Redo`（Windows/Linux 上通常是 Ctrl+Z / Ctrl+Y，macOS 是
Cmd+Z / Cmd+Shift+Z），並掛到整個主視窗（`mainWindow->addAction(...)`）讓快捷鍵在
任何 focus 狀態下都有效，不侷限在工具列按鈕本身。

圖示目前用 `QIcon::fromTheme("edit-undo"/"edit-redo")`，在有系統圖示主題的平台
（多數 Linux 桌面環境）會自動顯示對應圖示；Windows 上系統通常沒有這個主題，
會退化成純文字按鈕（不會壞掉，只是沒有圖）。如果想要自訂圖示，之後可以在建立
`QAction` 後補一行 `action->setIcon(QIcon("icons/xxx.png"))`，指到你自己準備的
圖檔即可。

### 已知限制 / 後續建議
- 目前 Sketch 通用 undo 的粒度是「一個 CommandManager 指令＝一筆 Undo」。如果你
  希望連續畫線時逐段都能各自 Undo（而不是整段折線一次復原），需要改成在
  `LineCommand` 內部每完成一段就各自 push 一次快照，而不是掛在
  `commandStarted`/`commandFinished` 這種「指令層級」的訊號上——這是可以做的，但
  和目前「不動 LineCommand 內部」的最小改動原則衝突，這次先沒做，先看看目前
  「整段折線一筆」的粒度夠不夠用。
- `HorizontalAlignmentEdit::setConstraintMode()`/`removeElement()` 目前是死碼，
  之後真的接上 UI 時記得補 undo push（見上方說明）。
